# Руководство программиста — OptimNet

OptimNet — десктопное приложение (Python ≥ 3.10, PyQt6) для оптимизации живучести
компьютерной сети. Методика и обозначения — в [`optim.md`](optim.md). Документ
описывает архитектуру, устройство модулей и порядок работы с кодом.

## 1. Архитектура

Проект построен по слоистой схеме с однонаправленными зависимостями:

```
gui/  ──────────────────────────────────────────────  слой представления
  │  читает/пишет
  ▼
state (AppState) ───────────────────────────────────  общее состояние
  │
  ▼
algorithms/  ──использует──►  core/  ───────────────  слой предметной области
  registry                        model, metrics,
  Optimizer                       problem, io
```

- **`core/`** не зависит от GUI и алгоритмов: модель сети, показатели
  (Q, Ψ, C_Σ, T_восст, λ_ab), постановки задачи и ввод/вывод. Этот слой можно
  использовать отдельно (скрипты, тесты, серверные задачи).
- **`algorithms/`** зависит только от `core.problem.Problem` — единой точки
  оценки решения. Новый алгоритм добавляется без правок в GUI.
- **`gui/`** зависит от обоих слоёв, но не наоборот: вся информация между
  вкладками передаётся через `AppState`.

### Поток данных при решении задачи

1. Пользователь загружает пример (JSON) или редактирует таблицы топологии;
   данные попадают в `AppState.network` и `AppState.scenarios` (`core.io`,
   `core.model`).
2. На вкладке «Задача» параметры постановки записываются в `AppState.config`
   (`core.problem.ProblemConfig`) и `AppState.critical_pairs`.
3. Вкладка «Эксперимент» конструирует `Problem(network, scenarios, config,
   critical_pairs)` и передаёт его в `ExperimentWorker` (поток `QThread`).
4. Алгоритм многократно вызывает `problem.evaluate(x)` и получает
   `EvalResult` (скалярная целевая F + все критерии + нарушения).
5. Через сигналы `pyqtSignal` прогресс и результаты возвращаются в GUI:
   таблица сравнения, график сходимости, визуализация решения на графе.
6. Результаты доступны для экспорта (CSV/JSON) и сохраняются в
   `AppState.last_results`.

Фоновые вычисления (`gui/workers.py`) гарантируют, что интерфейс не
блокируется: оптимизация выполняется в `QThread`, в GUI летят только сигналы
`progressed(iteration, best)` и `finished_ok(result)`. Остановка — через флаг
`_stop`, проверяемый в callback каждой итерации.

Общая схема работы приложения (ввод топологии → постановка → оптимизация в
фоновом потоке → результаты):

## 3. Модули core/

### `core/model.py` — модель данных

| Класс | Назначение |
|---|---|
| `Node` | Узел сети: `id`, `kind` (`router` \| `switch` \| `server`). |
| `Link` | Базовый канал (i, j): `capacity`, `cost`, `delay`, `reliability`. |
| `Demand` | Потребность в трафике: пара узлов + `volume` (участвует в Q). |
| `Candidate` | Кандидат на резервирование — возможный дополнительный канал; переменные решения строятся над пулом кандидатов. |
| `Scenario` | Сценарий поражения: `p`, `failed_nodes`, `failed_links`. |
| `Network` | Граф G = ⟨V, E, C, W⟩ вместе с потребностями и кандидатами; валидация ссылочной целостности (`validate`). |
| `Solution` | Вектор решения x: `discrete` (bool, выбранные кандидаты) и `continuous` (объёмы в [0, 1]); `volumes()` возвращает фактически добавленные доли ёмкости. |
| `CriticalPair` | Приоритетная пара (a, b) с требуемым уровнем резервирования `r_ab`. |

Все классы — `@dataclass` с парами `to_dict`/`from_dict` для сериализации.

### `core/metrics.py` — показатели (п. 2–4 optim.md)

- `Dinic` — реализация алгоритма Диница для максимального потока; написана
  руками (без networkx), чтобы работать быстро в горячем цикле оптимизации.
- `capacity_map(net, x, s)` — остаточные ёмкости в сценарии s: выжившие базовые
  каналы плюс доля ёмкости выбранных кандидатов (capacity · volume).
- `quality(net, x, s, mode)` — Q(x, s):
  - `mode="flow"` — доля доставленного трафика: потребности маршрутизуются
    последовательно через остаточные ёмкости (`_route_with_residual`);
  - `mode="connectivity"` — доля пар потребностей, сохраняющих связность хотя
    бы одним путём.
- `phi(q, q_min)` — пороговая функция φ.
- `survivability(net, x, scenarios, q_min, mode)` — Ψ(x) = Σ p(s)·φ(Q(x, s)).
- `cost(net, x)` — C_Σ(x) = Σ c_k·t_k по фактически добавленным объёмам.
- `recovery_time(net, x, scenarios, unit_time)` — упрощённая модель
  T = u·Σ p(s)·n(s)·(1−κ(s)): n(s) — число отказов без покрытия резервом на
  той же паре, κ(s) — доля отказавших каналов, имеющих такой резерв.
- `connectivity(net, x, s, pair)` — λ_ab: число непересекающихся по рёбрам
  путей (максимальный поток в графе с единичными ёмкостями).
- `minmax_normalize(value, lo, hi)` — нормировка критерия в [0, 1].

### `core/problem.py` — постановки и целевая функция

- `ProblemConfig` — параметры: `formulation`
  (`max_survivability` = 5.1, `min_cost` = 5.2, `minimax` = 5.3,
  `scalarized` = свёртка п. 6), `q_min`, `budget`, `psi_required`,
  `quality_mode`, `mode` (`discrete`/`continuous`/`mixed`), веса `weights`
  (α_Ψ, α_C, α_T, α_Q), `unit_time`, `penalty`.
- `Problem.evaluate(x) -> EvalResult` — единая точка входа для всех алгоритмов:
  1. вычисляет Q по всем сценариям, Ψ, C_Σ, T_восст, Q̄, min Q;
  2. собирает нарушения ограничений: бюджет, качество Q ≥ Q_min, связность
     λ_ab ≥ r_ab, для 5.2 — Ψ ≥ Ψ_треб;
  3. выбирает «сырое» направление цели по постановке
     (5.1: Ψ → max; 5.2: −C_Σ → max; 5.3: min Q → max; свёртка:
     Σ α_k·F̃_k → max с нормировкой);
  4. вычитает штраф `penalty · Σ(нарушений)²` — квадратичный штраф возвращает
     поиск в допустимую область;
  5. кэширует результат по ключу решения (округление непрерывной части до
     10⁻³) — в ГА/отжиге оценок много, повторы бесплатны.
- `Problem.random_solution(rng)` — случайное допустимое по типу решение.
- `EvalResult` — `objective` + все критерии + `feasible` + `violations`.

### `core/io.py` — ввод/вывод

- JSON: `load_example`/`save_example` (сеть + сценарии в одном файле),
  `load_network`/`save_network`, `load_scenarios`/`save_scenarios`.
- CSV: `save_network_csv`/`load_network_csv` (каталог с `nodes.csv`,
  `links.csv`, `demands.csv`, `candidates.csv`),
  `save_scenarios_csv`/`load_scenarios_csv` (один файл, множества через `;`,
  каналы — `ИСТОЧНИК-НАЗНАЧЕНИЕ`).
- `generate_scenarios(net, count, p_link, p_node, seed)` — автогенерация
  случайных отказов (штатный режим не генерируется).
- `export_result_csv(rows, path)`, `save_json(data, path)`.

### `core/logging_setup.py`

`setup_logging()` — корневой логгер `optimnet`: файл `optimnet.log` +
консоль; `get_logger(name)` — именованные дети (`optimnet.gui.experiment` и т.п.).
Повторный вызов `setup_logging` обработчики не дублирует.

## 4. Модули algorithms/

### `algorithms/base.py`

- `Optimizer` — абстрактный базовый класс: `optimize(problem, callback, seed)
  -> OptimizeResult`; `_run` замеряет время и число оценок.
- `Encoding` — кодирование решения вещественным вектором [0, 1]^n и обратно:
  `decode` (дискретная часть — порог 0.5; в смешанном режиме кандидат выбран,
  если объём > 0.05), `encode`, `random_vector`.
- `OptimizeResult` — лучшее решение, `EvalResult`, история лучшего значения по
  итерациям, число итераций/оценок, время, флаг остановки.
- `ProgressCallback = Callable[[int, float], bool]` — callback(iteration, best);
  возврат `False` останавливает алгоритм (используется кнопкой «Остановить»).

### Реализации

| Файл | Класс | Идея |
|---|---|---|
| `ga.py` | `GeneticAlgorithm` | Популяция векторов [0,1]^n; турнирная селекция (размер k), равномерный кроссинговер (вер. p_c), мутация (вер. p_m): инверсия бита в дискретном режиме / гауссово возмущение σ=0,2 в непрерывном; элитизм E особей. |
| `sa.py` | `SimulatedAnnealing` | Сосед — изменение одного гена; критерий Метрополиса `rand < exp(Δ/T)`; геометрическое охлаждение `T_k = T_0·q^k`; стоп по числу итераций или `T ≤ T_min`. |
| `bnb.py` | `BranchAndBound` | DFS по кандидатам; верхняя граница узла — Ψ на полном завершении (Ψ монотонно не убывает при добавлении каналов); ветвь «включить» обрезается бюджетом; лимит `max_nodes`. Только постановка 5.1, дискретный режим (проверяется явно). |
| `greedy.py` | `Greedy` | Пошаговое добавление кандидата с максимальным приростом F на единицу стоимости, пока есть бюджет и положительный прирост. |

### `algorithms/registry.py` — реестр и фабрика

- `ParamSpec` / `OptimizerSpec` — декларативное описание алгоритма: ключ,
  класс, параметры (подпись на русском, тип, границы, шаг), поддерживаемые
  постановки и режимы переменных.
- Параметры разбираются **автоматически из сигнатуры `__init__`** класса
  (`inspect.signature`), границы и русские подписи берутся из `_BOUNDS` и
  `_LABELS` — форма параметров на вкладке «Алгоритм» строится без правок UI.
- `OPTIMIZERS` — кортеж спецификаций; `available_optimizers(formulation, mode)`
  фильтрует по совместимости (например, bnb — только 5.1 + discrete);
  `create_optimizer(spec, **params)` строит экземпляр, игнорируя лишнее;
  `run_optimizer(spec, problem, params, callback, seed)` — обёртка «создать и
  запустить».

### Как добавить новый алгоритм

1. Унаследовать класс от `Optimizer`, реализовать `optimize` (с поддержкой
   `callback` и `seed`).
2. Добавить в `OPTIMIZERS` строку `OptimizerSpec("my", MyOptimizer,
   _params_from_signature(MyOptimizer))`; при необходимости — постановки/режимы
   и подписи в `_LABELS`/`_BOUNDS`.
3. Готово: вкладки «Алгоритм» и «Эксперимент» подхватят его автоматически.

## 5. Модули gui/

- `state.py` — `AppState`: `network`, `scenarios`, `config`,
  `critical_pairs`, `last_results`; `has_data()` — проверка минимума для
  запуска (узлы + потребности + сценарии).
- `main_window.py` — `MainWindow`: меню «Файл» (открыть/сохранить JSON,
  импорт/экспорт CSV, демо-примеры), 6 вкладок, строка статуса
  (число узлов/каналов/кандидатов/сценариев, Σp(s)); при старте загружает
  `examples/medium.json` и предлагает бюджет = 0,5·Σстоимостей кандидатов;
  синхронизирует списки алгоритмов при смене постановки/режима.
- `tab_topology.py` — редактируемые таблицы узлов/каналов/потребностей/
  кандидатов (внутренние вкладки), кнопка «Применить таблицы → модель»
  (валидация через `Network.validate`), граф сети.
- `tab_scenarios.py` — список сценариев + редактор (id, p, отказавшие узлы и
  каналы в формате `A-B`), генератор случайных отказов (seed, вероятности,
  режим «добавить к текущим»; иначе список заменяется на S0 (p=0,4) +
  сгенерированные с перенормировкой до 0,6), загрузка/сохранение JSON/CSV,
  сводка Σp(s) и числа отказов.
- `tab_problem.py` — выбор постановки (5.1/5.2/5.3/свёртка), варианта Q и типа
  переменных; параметры Q_min, C_бюдж, Ψ_треб, t_ед, штраф M; веса α_k с
  кнопкой нормировки Σα=1; таблица приоритетных пар (a, b, r_ab);
  «Применить к конфигурации задачи».
- `tab_algorithm.py` — выбор алгоритма из `available_optimizers` и форма
  параметров, построенная по `ParamSpec`.
- `tab_experiment.py` — выбор алгоритмов (флажки), число прогонов и базовый
  seed, запуск/остановка, сравнительная таблица (лучшее/среднее/худшее F,
  Ψ и C_Σ лучшего, средние время/итерации/оценки), график сходимости
  (`ConvergenceCanvas`, matplotlib), экспорт таблицы CSV и результатов JSON.
  Параметры берутся из вкладки «Алгоритм» для выбранного там алгоритма,
  остальные — значения по умолчанию из реестра.
- `tab_results.py` — выбор результата, сводка по критериям и нарушениям,
  таблица решения x (кандидаты с объёмами и стоимостью), таблица Q(x, s) и
  φ(Q) по сценариям, кнопка «Показать решение на графе» (переход на вкладку
  «Топология» с зелёной подсветкой резервных каналов), экспорт CSV/JSON
  (`result_to_dict` — единый формат результата).
- `graph_canvas.py` — `NetworkCanvas` (matplotlib): базовые каналы серые,
  отказы сценария — красный пунктир, резервные каналы решения — зелёные
  жирные с подписью объёма, отказавшие узлы — красная кайма; раскладка —
  spring_layout (seed=42); легенда.
- `workers.py` — `OptimizeWorker` (один прогон) и `ExperimentWorker`
  (поочерёдно все алгоритмы × прогоны) на `QThread`; сигналы прогресса и
  результата; `_run_timed` заполняет `runtime` и число новых оценок.

## 6. Форматы данных

### JSON примера (examples/*.json)

```json
{
  "nodes": [{"id": "R1", "kind": "router"}],
  "links": [{"source": "R1", "target": "R2", "capacity": 10,
             "cost": 2.0, "delay": 0.0, "reliability": 0.99}],
  "demands": [{"source": "S1", "target": "S2", "volume": 8.0}],
  "candidates": [{"id": "C1", "source": "R1", "target": "R4",
                  "capacity": 10.0, "cost": 4.0}],
  "scenarios": [{"id": "S0", "p": 0.4, "failed_nodes": [],
                 "failed_links": [["R1", "R3"]]}]
}
```

`kind` ∈ {router, switch, server}; у каналов `cost`, `delay`, `reliability`
необязательны (умолчания 1.0 / 0.0 / 0.99).

### CSV

Топология — каталог с `nodes.csv`, `links.csv`, `demands.csv`,
`candidates.csv` (заголовки как в JSON). Сценарии — один файл
`id,p,failed_nodes,failed_links`; множества через `;`, канал — `A-B`.

### Результат экспорта (JSON)

См. `result_to_dict` (gui/tab_results.py): `algorithm`, `objective`, `psi`,
`cost`, `t_recovery`, `q_mean`, `q_min_actual`, `feasible`, `violations`,
`iterations`, `evaluations`, `runtime_sec`, `solution` (выбранные кандидаты с
объёмами), `per_scenario` (Q и φ по каждому сценарию).

## 7. Тестирование

```bash
.venv/Scripts/python.exe -m pytest tests/ -q     # Windows
```

- `tests/conftest.py` — эталонная малая сеть (A→B→C, потребность A→C объём 8,
  Q без резерва = 7/8 = 0,875) и сценарии S0/S1.
- `tests/test_metrics.py` — Q(x, s), φ, Ψ, C_Σ, T_восст, λ_ab.
- `tests/test_problem.py` — целевая функция, штрафы, кэширование, постановки.
- `tests/test_algorithms.py` — запуск всех алгоритмов, допустимость решений,
  кодирование/декодирование.
- `tests/test_io.py` — круговые преобразования JSON/CSV, генерация сценариев.

UI и алгоритмы получают показатели из одного источника (`core.metrics`), поэтому
значения Ψ и Q в интерфейсе совпадают с unit-тестами.

## 9. Соглашения по разработке

- Комментарии и docstring — на русском языке; имена идентификаторов — английские.
- Обозначения показателей в коде и документах совпадают с `doc/optim.md`:
  Ψ → `survivability`, φ → `phi`, Q_min → `q_min`, C_Σ → `cost`,
  λ_ab → `connectivity`, α_k → `weights`.
- Случайность везде проходит через `numpy.random.default_rng(seed)` — прогоны
  воспроизводимы при заданном seed.
